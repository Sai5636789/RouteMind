# Data model

PostgreSQL 16 with PostGIS. The schema is owned by Flyway migrations
in `backend/src/main/resources/db/migration/`; Hibernate validates it
(`ddl-auto: validate`) and never creates or alters tables. Every table
uses a UUID primary key generated by the database, plus `created_at`
and `updated_at` timestamps.

## depots (V1)

The single depot the fleet operates from.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `name` | VARCHAR(100) | Not null |
| `address` | TEXT | |
| `location` | GEOGRAPHY(Point, 4326) | Not null; the depot is at longitude -82.3248, latitude 29.6516 (Gainesville, FL) |

Seeded by V1 as `Gainesville Depot`. The depot id is looked up, never
hard-coded, by later migrations.

## vehicles (V2, status extended in V3)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `plate_number` | VARCHAR(12) | Not null, unique |
| `model` | VARCHAR(100) | Not null |
| `capacity_kg` | NUMERIC(10, 2) | Not null, must be over 0 |
| `status` | VARCHAR(20) | Not null, default `AVAILABLE` |
| `depot_id` | UUID | References `depots(id)` |

Status is one of `AVAILABLE`, `ON_ROUTE`, `MAINTENANCE`,
`OUT_OF_SERVICE`, `BROKEN_DOWN`. `BROKEN_DOWN` is set only by the
incident flow. Indexed on `status`.

## drivers (V2)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `first_name` | VARCHAR(50) | Not null |
| `last_name` | VARCHAR(50) | Not null |
| `license_number` | VARCHAR(30) | Not null, unique |
| `phone` | VARCHAR(20) | |
| `status` | VARCHAR(20) | Not null, default `ACTIVE` |

Status is one of `ACTIVE`, `ON_LEAVE`, `INACTIVE`. Indexed on `status`.

## orders (V2, flag added in V3)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `customer_name` | VARCHAR(100) | Not null |
| `delivery_address` | TEXT | Not null |
| `latitude` | DOUBLE PRECISION | Not null, -90 to 90 |
| `longitude` | DOUBLE PRECISION | Not null, -180 to 180 |
| `weight_kg` | NUMERIC(10, 2) | Not null, must be over 0 |
| `status` | VARCHAR(20) | Not null, default `CREATED` |
| `assigned_vehicle_id` | UUID | References `vehicles(id)` |
| `assigned_driver_id` | UUID | References `drivers(id)` |
| `needs_reassignment` | BOOLEAN | Not null, default false; set only by a breakdown |

Status is one of `CREATED`, `ASSIGNED`, `IN_TRANSIT`, `DELIVERED`,
`CANCELLED`. The assignment rule is enforced in the database: an
order is either unassigned, or assigned to both a vehicle and a
driver; half-assigned orders cannot exist. Delivery position is stored
as plain latitude and longitude columns; the geography point used by
routing is derived from them when needed.

Indexed on `status`, `assigned_vehicle_id`, `assigned_driver_id`, and
`needs_reassignment` (partial index, only rows where it is true).

## incidents (V3)

One row per breakdown: which vehicle, why, and whether it is still open.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `vehicle_id` | UUID | Not null, references `vehicles(id)` |
| `reason` | TEXT | |
| `status` | VARCHAR(20) | Not null, default `OPEN` |
| `reported_at` | TIMESTAMPTZ | Not null, default now |
| `resolved_at` | TIMESTAMPTZ | Set on resolve |

Status is one of `OPEN`, `RESOLVED`. Indexed on `status` and
`vehicle_id`.

## incident_orders (V3)

One row per order a breakdown affected: the status the order had when
it lost its vehicle, and the vehicle it was rerouted to, if any.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `incident_id` | UUID | Not null, references `incidents(id)` |
| `order_id` | UUID | Not null, references `orders(id)` |
| `previous_status` | VARCHAR(20) | Not null |
| `reassigned_vehicle_id` | UUID | References `vehicles(id)`, null until rerouted |

Unique on (`incident_id`, `order_id`). Indexed on `incident_id`.

## dispatch_plans (V4)

One row per saved optimization run: which depot it started from,
whether it was approved, and the measured totals from the matrix the
optimizer used.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `depot_id` | UUID | Not null, references `depots(id)` |
| `status` | VARCHAR(20) | Not null, default `DRAFT` |
| `matrix_source` | VARCHAR(20) | Not null; OSRM road times or straight-line |
| `total_distance_metres` | DOUBLE PRECISION | Not null, default 0 |
| `total_duration_seconds` | DOUBLE PRECISION | Not null, default 0 |
| `total_weight_kg` | DOUBLE PRECISION | Not null, default 0 |
| `decided_at` | TIMESTAMPTZ | Set when approved, rejected or cancelled |

Status is one of `DRAFT`, `APPROVED`, `REJECTED`, `COMPLETED`,
`CANCELLED`. Indexed on `status`.

## dispatch_stops (V4)

One row per order on a plan, in visit order.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `plan_id` | UUID | Not null, references `dispatch_plans(id)` |
| `vehicle_id` | UUID | Not null, references `vehicles(id)` |
| `driver_id` | UUID | References `drivers(id)`; may be set after the plan is created, must be set before approval |
| `order_id` | UUID | Not null, references `orders(id)` |
| `stop_index` | INTEGER | Not null; visit order within the plan |
| `status` | VARCHAR(20) | Not null, default `PENDING` |
| `route_distance_metres` | DOUBLE PRECISION | Not null, default 0; the whole route measured totals, repeated on each of its stops |
| `route_duration_seconds` | DOUBLE PRECISION | Not null, default 0 |

Status is one of `PENDING`, `PICKED_UP`, `DELIVERED`, `FAILED`,
`CANCELLED`. Unique on (`plan_id`, `order_id`). Indexed on
(`plan_id`, `stop_index`) and on `driver_id`.

## Sample demo dataset (V5)

A fresh database starts useful the moment the stack is up:

- 8 vehicles (`VAN-001` to `VAN-008`) at the Gainesville depot,
capacities 100 to 300 kg, all `AVAILABLE`.
- 8 active drivers.
- 24 unassigned `CREATED` orders at real Gainesville locations,
weights 11 to 40 kg, 550 kg in total, more than any one vehicle
carries, so the optimizer has to split the work across the fleet.

Nothing is pre-assigned: the dispatcher still creates the plan,
approves it, and works the deliveries. To start over, drop the
database volume (`docker compose down -v`) and start again; Flyway
applies V1 to V5 on first boot.

## Redis (not Postgres)

Live positions live in Redis, not in the database:

- `tracking:vehicles:geo`, a GEO set with the latest position per
vehicle, plus a per-vehicle hash and an id set.
- The GPS simulator moves every on-route vehicle along its assigned
stops at a configurable speed (default 40 km/h, 5 second tick) and
stores each position there.
- Positions are only ever recorded for vehicles the simulator has
actually moved. Nothing in Redis is the source of truth for order,
vehicle or driver state; Postgres is.
